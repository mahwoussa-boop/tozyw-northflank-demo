# خطة النظام التدريجي الحدثي — مهووس (Event-Driven Incremental)

> **الحالة:** مسوّدة معمارية للموافقة — *لا كود بعد*. بُنيت على تحقيق فعلي في الشيفرة (grep/read + استعلامات `mode=ro`) بتاريخ 2026-07-11.
> **الهدف من المالك:** «أضف منافساً ⇒ يكشط ويحلّل تلقائياً؛ أرسل منتجاً ⇒ يدخل منتجاتي للمقارنة؛ العمل أوتوماتيكي بلا كاش وبيانات مكدّسة تُثقل التطبيق — نظام قويّ واضح لا يكسر.»

---

## 0) المبدأ الحاكم (جوهر «لا يكسر»)

المشكلة ليست وجود الكاش، بل **نوعه**: لديك لقطة JSON بحجم 62MB يُعاد بناؤها بالكامل مع كل ضغطة زر. الحلّ ليس «إلغاء الكاش» (سيصير أبطأ — تجميعة السوق وحدها 39 ثانية)، بل:

> **مصدرٌ واحد للحقيقة في SQLite، يُحدَّث تدريجياً صفّاً صفّاً، ويُقرأ بفهرسة سريعة — مع تشغيلٍ ليليٍّ كامل يبقى المرجعَ الذي يصحّح أي انحراف.**

هذا نمط هندسي معروف وحديث: **الاتساق التدريجي + المصالحة** (*eventual consistency + reconciliation*). التحديث التدريجي يعطي استجابة فورية للشاشة؛ التشغيل الليلي الكامل (موجود أصلاً 04:30) هو الحَكَم النهائي. **بهذا لا نطلب من التحديث التدريجي أن يكون مثالياً 100% — بل «جيّداً فوراً، ومثالياً بحلول الصباح».** وهذا بالضبط ما يمنع الكسر على متجر حيّ.

## 1) التشخيص المُثبَت (أرقام لا انطباعات)

| المُلاحَظة | الدليل |
|---|---|
| لقطة `ui_session.json` 62MB تُعاد كتابتها في **~22 موضعاً** (كل ضغطة إرسال/إخفاء/استرجاع) | `ui/state_manager.py:227` + ~22 نداءً لـ`persist_results()` |
| مجموع الكتل العملاقة **~163MB** (`ui_session` 62 + `missing_cache` 57 + `pricing_cache` 44) | `data/` فعلياً |
| **11 صفحة من 17** تقرأ من اللقطة في الذاكرة؛ **3 فقط** تقرأ SQLite حيّاً | جدول التصنيف §Q3 من التحقيق |
| التطبيق **متزامن**: الكشط يُجمِّد الواجهة تحت `st.spinner` | `ui/pages/scraper.py:69-71,103-105` |
| موجّه الذكاء على دفعة المراجعة هو **عنق زجاجة السرعة** (تشغيل كامل تجاوز 45 دقيقة) | `bootstrap.py:365-400` + `services/ai_router_service.py` |

**الخلاصة:** الثقل مصدره الأساسي *طبقة اللقطة* لا منطق التحليل. لذا أكبر مكسب (المرحلة 1) لا يلمس التسعير/المطابقة إطلاقاً.

## 2) ما هو مبنيٌّ بالفعل (نبني عليه لا من الصفر)

| القدرة المطلوبة | الموجود فعلاً | الناقص فقط |
|---|---|---|
| «أضف منافساً ⇒ اكشط» | `scrape_and_save(comp, rebuild=True)` يكشط + **يحدّث بالاستبدال** (`UNIQUE(competitor,norm_name)`) + يعيد بناء كاش الرادار | **ربطه** بزر الإضافة + جعله **خلفياً** |
| «تخزين مشتقّ ذرّي» | `rebuild_opportunity_scores()`: `DELETE+INSERT` داخل معاملة واحدة، قراءة `mode=ro` مفهرسة، جدول فارغ ⇒ `[]` بلا كسر | تعميم النمط على الأقسام |
| «أرسل منتجاً ⇒ سجِّله» | `export_service.post_to_make()` يكتب `send_log` لكل منتج؛ `upsert_our_catalog()` يُدرج في `our_catalog` | إدراج صفّ `our_catalog` عند نجاح الإرسال |
| «سجلّ تغييرات» (CDC) | `product_signal_events` (170k صفّ append-only) يسجّل كل تحوّل أثناء الكشط | استغلاله للتحديث التدريجي |
| «مهام مجدولة» | `rebuild_radar.bat` (04:30) عبر مجدول ويندوز + واجهة `TaskScheduler` نائمة | تشغيل خلفي داخل العملية |

**نتيجة مهمّة:** 70% من رؤيتك موجود كلبنات؛ العمل الحقيقي هو **الربط + التخزين التدريجي + عامل خلفي واحد**، لا إعادة كتابة المحرّك.

## 3) البنية المستهدفة (صورة واضحة)

```
        حدث المستخدم                     مصدر الحقيقة (SQLite)              القراءة
   ┌────────────────────┐          ┌──────────────────────────┐      ┌──────────────┐
   │ أضف منافساً         │──enqueue─▶│  jobs (طابور دائم)        │      │ صفحات الأقسام │
   │ أرسل منتجاً          │          │  competitor_products_store│─────▶│ تقرأ مفهرَساً │
   │ أخفِ/استرجع         │──upsert──▶│  our_catalog              │      │ + ترقيم صفحات│
   └────────────────────┘          │  sections_store (جديد)    │      └──────────────┘
             │                      │  opportunity_scores       │
             ▼                      │  ui_state (جديد، صغير)    │
   ┌────────────────────┐          └──────────────────────────┘
   │ عامل خلفي واحد      │──atomic────────────▲   ▲
   │ (background worker) │  DELETE+INSERT      │   │
   └────────────────────┘                     │   │
             ▲                                 │   │
   ┌────────────────────┐   مصالحة ليلية كاملة  │   │  ← الحَكَم النهائي (يصحّح أي انحراف)
   │ 04:30 التشغيل الكامل│──────────────────────┘   │
   └────────────────────┘                           │
   (اللقطة العملاقة 62MB تُحذف — لم تعد مسار القراءة)
```

المبادئ الحديثة المطبَّقة صراحةً:
- **Outbox / طابور مهام دائم** (`jobs` في SQLite): الكشط لا يُجمّد الواجهة، وينجو من إغلاق التطبيق.
- **Idempotency:** كل كتابة عبر *upsert* بمفتاح طبيعي (`competitor+norm_name` / `product_id`) ⇒ التكرار آمن، لا تكديس.
- **معاملات ذرّية:** نمط الرادار (`DELETE+INSERT` في معاملة، تراجع كامل عند الفشل).
- **مصدر واحد للحقيقة:** SQLite (WAL مفعّل)، والقراءة `mode=ro` مفهرَسة + ترقيم صفحات (لا تحميل 11k صفّ للذاكرة).
- **تدهور رشيق (graceful degradation):** أي اعتماد جديد يفشل «مفتوحاً» ⇒ الصفحة تتصرّف كما اليوم بالضبط.
- **CDC:** `product_signal_events` سجلّ تغييرات جاهز نبني عليه الإشعارات/التحديثات.

## 4) المراحل — كلٌّ كتلة مستقلّة، قابلة للتراجع، بوّابة اختبارات خضراء

> ترتيب موصى به: **المرحلة 1 أولاً** (أكبر راحة، أقل خطر، مستقلّة عن صحّة التحليل)، ثم 0 ⇐ 2 ⇐ 3 ⇐ 4. كلّ مرحلة تمرّ بموافقتك.

### المرحلة 1 — إزالة الثقل (الأعلى قيمة، الأقل خطراً)
**لا تلمس منطق التسعير/المطابقة إطلاقاً — تغيّر التخزين والقراءة فقط.**
1. انقل الحالة المتغيّرة الصغيرة (`processed_price_skus` / `processed_missing_urls` / `hidden_products` / `processed_log`) إلى جدول `ui_state` صغير (upsert لكل فعل، بدل إعادة كتابة 62MB).
2. جسِّد الأقسام الخمسة + `missing_df` في جدول `sections_store` يُكتب **مرّة** بعد كل تحليل (ذرّياً)، وتقرأه الصفحات مفهرَساً + ترقيم صفحات.
3. أحِل `ui_session.json` من مسار القراءة (يبقى مؤشّر صغير للتوافق)، ثم احذف الكتل الثلاث (163MB).
4. حدِّث السكربتات المستقلّة التي تفترض وجود اللقطة (`redistribution_dryrun/apply`، `_run_review_full`، `perf_baseline`، `backup_data`).
- **الحاجز:** المحاسبة المغلقة 0% تبقى (المنطق لم يُمَسّ)؛ الاختبارات خضراء؛ حالات فارغة رشيقة؛ قياس زمن الفتح قبل/بعد (رقم لا وصف).

### المرحلة 0 — أساس الخلفية (تمهيد للمرحلتين 2 و3)
1. جدول `jobs` دائم (نوع، حمولة، حالة، محاولات، طابع زمني) — نمط outbox.
2. عامل خلفي واحد داخل العملية خلف واجهة `TaskScheduler` القائمة (بلا تغيير واجهتها العامّة) — أول تنفيذ خلفي حقيقي في التطبيق.
- **الحاجز:** الطابور ينجو من إعادة التشغيل؛ عامل واحد فقط (لا سباق)؛ WAL؛ كل مهمة idempotent وتُسجَّل تقدّمها في `job_progress`.

### المرحلة 2 — «أضف منافساً» أوتوماتيكي
1. اربط `add_competitor` بإدراج مهمة `scrape` في الطابور فوراً.
2. العامل الخلفي ينفّذ `scrape_and_save(comp)` (كشط + upsert + إعادة بناء كاش الرادار — موجود)، ثم إشعار عند الانتهاء.
3. مدّد قفل الكشط ليشمل الكشط الفردي (اليوم يحمي «اكشط الكل» فقط) لمنع تضارب نفس المتجر.
- **الواقع بصراحة:** الكشط شبكيّ (دقائق) ⇒ «أوتوماتيكي» = **خلفي + إشعار**، لا لحظي.
- **الحاجز:** upsert (لا تكديس)؛ فشل الكشط يُعاد ويُسجَّل؛ الواجهة تُظهر الحالة؛ لا تجميد.

### المرحلة 3 — «أرسل منتجاً» يدخل منتجاتي فوراً
1. عند نجاح الإرسال (نقطة الاختناق المشتركة `export_service.post_to_make` للمنتج الجديد، أو `card_actions.py:134` لكل ضغطة) أدرِج صفّاً في `our_catalog` (يحاكي `upsert_our_catalog`).
2. يظهر فوراً في «منتجاتي» + يرفع علم `in_our_catalog` في الرادار.
3. **تصنيفه في القسم الصحيح:** مبدئياً إدراج في `our_catalog` الآن، وتصنيفه النهائي في المصالحة الليلية (لأن التصنيف الفوري المثالي يحتاج حالة الماركات العامّة — انظر §5). لاحقاً (اختياري): تصنيف تفاؤلي فوري بدفعة ذكاء من عنصر واحد.
- **الحاجز:** الإرسال الحيّ يبقى **خلف موافقتك**؛ التلقائي هو الكتابة المحلّية فقط؛ upsert بمفتاح `product_id/norm_name` (لا تكرار).

### المرحلة 4 — المصالحة الليلية (الحَكَم — ما يجعل التدريجي آمناً)
1. وسِّع مهمّة 04:30 لتشغّل **التحليل الكامل** (لا كاش الرادار فقط) وتبدّل `sections_store` ذرّياً.
2. أي انحراف تدريجي (تصنيف مؤقّت خاطئ، «مفقود» عابر) يُصحَّح خلال 24 ساعة **بضمان**.
- **الحاجز:** التشغيل الكامل يبقى مرجع المحاسبة المغلقة 0%؛ التبديل ذرّي؛ فشل ⇒ يبقى القديم.

## 5) المخاطر الصريحة وتخفيفها (لا وعود زائفة)

| الخطر | لماذا حقيقي (بالدليل) | التخفيف |
|---|---|---|
| التدريجي ≠ الكامل تماماً | حالة `KNOWN_BRANDS` عامّة تُجمَّد بعد أول تشغيل (`engine.py:295-346`)؛ دمج «الأرخص عبر المتاجر» للمفقودات (`engine.py:3444-3512`)؛ السجلّ الكمومي يتوازن على الكون الكامل فقط (`closed_loop_engine.py:1799-1804`) | **المصالحة الليلية مرجعية**؛ التدريجي «تفاؤلي للعرض» فقط |
| أول تزامن داخل العملية | لا عامل خلفي حيّ اليوم (كله متزامن) | طابور دائم + عامل واحد + WAL + idempotency |
| «فوري» للكشط وهم | الكشط شبكيّ محافظ (تزامن 3 للتخفّي) | إطار توقّع صريح: خلفي + إشعار |
| بطء التحليل | موجّه الذكاء دفعات شبكية (عنق الزجاجة الحالي) | التدريجي يتخطّى الذكاء؛ الليلي يفعّله كاملاً |
| حذف اللقطة يُفرِغ 11 صفحة | مسار القراءة الحالي منها | لا نحذف قبل أن تقرأ الصفحات SQLite (المرحلة 1 تسبق الحذف) |

## 6) ثوابت لا تُمَسّ (byte-identical)

- **التطبيع/المطابقة/التسعير/التصدير:** `engine.normalize/normalize_name/extract_*`، `matching_service` primitives، `closed_loop_engine.normalize_text`، وأعمدة `export_service` (صيغة سلك Make/سلة). كلّها `#PRESERVED_LOGIC` (≈90 موضعاً).
- **سلاسل القرار:** `🔴 سعر أعلى / 🟢 سعر أقل / ✅ موافق / ⚠️ تحت المراجعة / ⚪ مستبعد` وعتبات 60/85 وربط البادئة←القسم.
- **دفتر المحاسبة المغلقة:** `CompetitorLedger` (`closed_loop_engine.py`) والقانون «المدخل = المتطابق + المراجعة + المفقود».
- **الأرشيفات append-only:** `price_history` / `events` / `product_signal_events` — لا UPDATE/DELETE. الكاش الوحيد المسموح فيه DELETE+INSERT: `opportunity_scores` (ويُضاف `sections_store` بالتعيين الصريح).

## 7) طريقة العمل لكل كتلة (بروتوكول التنفيذ)

`[أ]` كتلة كاتبة: فرع جديد + وسم رجوع (`green-<N>`) + بوّابة الاختبارات (الأساس الحيّ = **1217** بتاريخ 2026-07-11) قبل/بعد كل خطوة + commit لكل خطوة + الخطوة 0 «تثبيت» تُعيد قراءة الأسطر الحيّة + تنتهي على master + تقرير مرقّم + سطر نقطة التوقف. تعديل ≤~30 سطراً لكل ملف إنتاجي/خطوة. **لا `--no-verify`.** كل كتلة تمرّ بموافقتك — **لا استمرار تلقائي عبر الكتل.**

## 8) القرار المطلوب منك الآن

هذه المسوّدة تُثبّت الاتجاه والحواجز. عند موافقتك، أبدأ بـ**المرحلة 1** (إزالة الثقل) بكتلة استطلاع `[ب]` أولاً ثم تنفيذ `[أ]` — دون لمس منطق التسعير. أي مرحلة أو ترتيب مختلف = قرارك.
